## 1. 后端：结构化诊断报告与分类器

### 1.1 数据结构（新模块 `src-tauri/src/diagnosis.rs`）

```rust
pub struct DiagnosisReport {
    pub target: String,              // analysis | transcription
    pub stage: DiagnosisStage,       // catalog | inference | model | protocol | quota | network | response | format | ok
    pub status: String,              // passed | failed
    pub model: String,
    pub http_status: Option<u16>,
    pub error_code: Option<String>,          // 服务商 error.code / error.type，脱敏后
    pub provider_message: Option<String>,    // sanitize_provider_message 输出，≤500 字
    pub tested_at: String,
    pub suggested_action: SuggestedAction,   // 结构化键，前端映射中文
}
pub enum SuggestedAction { RefillKey, SwitchModel, CheckAccount, CheckNetwork, Retry, ChangeModelOrPermission }
```

### 1.2 分类规则（错误码优先，HTTP 状态仅辅助）

输入：阶段上下文（目录/推理）、HTTP 状态、解析出的 error code/type、传输错误类型。

| 上下文 | 信号 | stage | suggested_action |
|---|---|---|---|
| 目录 | transport/timeout | network | CheckNetwork |
| 目录 | 401/403 | catalog | RefillKey |
| 目录 | 其他 4xx/5xx | catalog | CheckAccount |
| 推理 | error code 含 model_not_found / invalid_model / unknown model | model | SwitchModel |
| 推理 | 401/403（无可靠错误码） | inference | **ChangeModelOrPermission**（双动作：换模型 + 查账号权限；不得单独断言 Key 无效） |
| 推理 | 404 | model | SwitchModel |
| 推理 | 400 / unsupported | protocol | SwitchModel |
| 推理 | 429 | quota | Retry |
| 推理 | transport/timeout | network | CheckNetwork |
| 推理 | 200 但响应无内容 | response | Retry（附脱敏技术详情） |
| 推理 | 200 有内容但非合法 JSON（分析） | format | SwitchModel |

- 服务商响应解析顺序：`error.code` → `error.type` → `message`（全部经现有脱敏链）；无法可靠分类时落到 ChangeModelOrPermission。
- 所有服务商原文经 `sanitize_provider_message`（external_asr.rs:712-731，凭据替换 + 截断）。**修复风险点**：models 错误路径当前只 truncate 不脱敏（commands.rs:3028-3039），统一改走脱敏版。
- 任何路径不得把请求头、完整错误体、Key 写入报告或日志。

## 2. 草稿诊断命令（不落盘）

### 2.1 命令签名（commands.rs，与现有外部命令同区）

```rust
pub async fn diagnose_external_provider(
    target: String, provider_id: String, base_url: String, model: String,
    credentials: BTreeMap<String, String>,   // 表单新凭据；空 = 回退已保存
) -> Result<DiagnosisReport, String>          // report 内含 verification_token（成功时）
```

- BTreeMap 支持腾讯云三字段（风险点 8：现有 set_external_ai_api_key 只支持单 Key）。
- **凭据优先级**：参数非空只用参数（绝不读 env/Keychain，防测错 Key）；参数为空时回退当前槽位已保存凭据，且必须满足 `saved_provider == provider_id`（沿用 list_external_models 的模式，commands.rs:3098-3110），不一致直接报「请先填写凭据」。
- 回退路径沿用现有 `get_credentials_with_account` 语义（env 优先于 Keychain）——与「验证已保存配置」保持同一套取 Key 语义，不造第二套。
- 不写 DB、不写 Keychain、不返回任何凭据值。

### 2.2 分析探测（不走 complete_text 的 3 次重试，防吞错）

- 固定提示词复用 `OpenAiCompatibleClient::test` 的 `Return exactly this JSON object: {"ok":true}`（memory.rs:256-267），但新写一次性请求函数（无重试循环，单次 30s 总超时）。
- 200 且响应含合法 JSON → passed；200 有内容非 JSON → format；其余按 1.2 分类。
- 不携带用户录音/逐字稿/知识库内容。

### 2.3 转写探测

- 复用 1 秒 440Hz 正弦测试音生成（external_asr.rs:86-92）。
- 新写接受显式 provider/base_url/credentials 的探测入口（**不可复用** `probe_external_asr_connection`，它经 transcribe_with_transport 读 DB，external_asr.rs:83-108）；协议分发复用 `send_transcription_request`（external_asr.rs:116-136）。
- 单次 30s 总超时（区别于正式转写 300s）。

### 2.4 安全链（全数复用现有函数，顺序固定）

`resolve_base_url`（内置地址锁定，provider_catalog.rs:503-529）→ `validate_external_base_url`（HTTPS 强制 + loopback 例外，memory.rs:81-141）→ 构造 endpoint → `assert_endpoint_still_safe`（DNS rebinding 复校，memory.rs:145-162）→ reqwest agent `redirects(0)` + connect 10s + 总 30s → **响应体上限 64KB，超出截断后按截断文本参与分类**（任务书 3.2 要求的响应体大小限制）→ sanitize + truncate。固定请求方法与固定测试请求体，不接受调用方注入任意路径/Header/请求体。URL 长度 ≤500。

## 3. 一次性验证票据（进程内存）

- `VERIFY_TICKETS: OnceLock<Mutex<HashMap<String, VerifyTicket>>>`（放 state.rs，仿 EXPORT_TICKETS 先例 state.rs:95-100）。
- `VerifyTicket { target, provider_id, base_url（规范化后）, model, credentials_digest, expires_at, used }` —— **票据必须绑定 target**：analysis 诊断签发的 token 不得用于 transcription 的 save_and_verify（校验含 target 全等），防止「已验证」建立在错误能力的探测上。
- `credentials_digest` = HMAC-SHA256(**解析后的凭据集合**, 进程随机密钥)。digest 按诊断命令实际使用的凭据集合计算（含空凭据回退已保存集合的情形），save_and_verify 端按同一解析语义重算——即「回退路径两次解析结果」而非表单原文，避免空凭据场景永远拒绝。
- 进程密钥 `DIAGNOSIS_HMAC_KEY: OnceLock<[u8; 32]>`，首次访问由 uuid v4 字节熵填充（Cargo.toml 无 rand；uuid/sha2/hmac 已在），不落盘、不返回前端。
- 票据 TTL 10 分钟，诊断成功时签发，随 DiagnosisReport 返回；save_and_verify 携带并校验：存在 + 未过期 + 未使用 + **target**/provider/baseUrl/model/digest 全匹配 → 标记 used（一次性）。任一不符 → 拒绝复用旧验证结果，要求重新测试。
- 不跨重启（纯内存）；token 本身是随机串，无敏感信息。
- 已记录决定：多窗口/重复打开设置页 = last-writer-wins（后端票据全局共享，revision 机制保证最终一致）；token 前端只存组件态，重挂载即失效要求重测（保守正确）。

## 5. 保存 / 验证解耦（后端编排）

三个命令：

1. `save_provider_config`（纯保存，不验证）：写 settings + 凭据（revision+1），健康快照不动 → 前端状态按 §7.1 推导为 **stale**（旧快照存在但 revision 不匹配；无旧快照则 unverified）。**原子化**：settings+revision+health 更新为**单个 SQLite 事务**（沿 update_external_ai_settings 事务模式，settings.rs:288-312）；先读旧值入内存，Keychain 写失败或 DB 写失败 → 尽力回滚已写部分（**env 命中时回滚目标=删除 Keychain 条目而非回写 env 值**，避免改变存储语义）；回滚失败返回 `SaveOutcome { saved: Vec<步骤>, rolled_back: Vec<步骤>, partial: bool }`，前端拿到 partial 后强制重新读取后端真实状态，不信任本地乐观状态。已接受并记录的时间窗：Keychain 已写、DB 未写的间隙内，后台任务理论上可读到新凭据发起请求——桌面端单用户场景可接受，不做槽位锁。
2. `save_and_verify_provider(draft..., verification_token)`：先校验票据（§3）→ 通过才提交（同 1 的原子流程）→ 成功后写 provider_health(passed)。票据无效 → 整体拒绝，原保存配置**完全不变**。诊断失败时根本不会走到提交。
3. `verify_saved_provider(target)`：对已保存配置跑诊断（凭据回退路径）→ 更新 provider_health（passed 或 failed），revision 取当前值。

提交顺序固定：凭据 → settings（provider/base_url/model/consent/enabled）→ revision+1 → health 快照。target 变更时现有的 consent/enabled 重置逻辑（settings.rs:250-272）保留，但重置发生在**验证通过之后的提交阶段**，草稿诊断阶段不触碰任何状态。

## 7. 前端：六态状态机与状态条

### 7.1 状态推导（`deriveVerifyState(settings, health, revision, catalogVersion, draft)`）

```
unconfigured   无凭据或 provider 为空（清除凭据后立即回到此态）
unverified     配置齐全但无任何快照
verifying      请求进行中（busy，唯一由运行时标志决定）
verified       快照 passed 且 provider/baseUrl/model/revision/catalogVersion 全匹配
stale          有快照但任一字段不匹配，或本次会话内用户编辑过凭据/模型/provider 未保存
failed         快照 failed 且字段匹配
```

**推导优先级链（自上而下命中即停）**：
1. `unconfigured`（无凭据或 provider 为空）；
2. `verifying`（请求进行中，覆盖一切快照态）；
3. 草稿偏离（凭据已编辑，或 provider/baseUrl/model 草稿 ≠ 已存）→ stale（文案「配置已修改，保存后需重新验证」）；
4. 无快照 → unverified；
5. 快照字段匹配 + passed → verified；
6. 快照字段匹配 + failed → failed（草稿偏离时不显示旧失败原因，stale 优先于 failed——失败结论只对产生它的配置指纹负责）；
7. 有快照但字段不匹配 → stale。

- 草稿偏离已存（provider/model/baseUrl 编辑）→ 状态条显示「配置已修改，保存后需重新验证」；草稿切回原值且凭据未动 → 恢复快照态（指纹完整匹配即恢复，任务书 3.3）。
- 凭据输入一旦被编辑（draftCredentials 非空）→ 强制 stale，直到保存（revision 变化使旧快照失效）。
- 清除凭据：provider_health 快照**保留**（历史失败原因可复查），由 unconfigured 优先级屏蔽显示；revision+1 使其永不复用。
- 仅保存（无票据）→ unverified 或 stale（§5.1）。
- 状态条独立组件 `VerifyStatusPill`，`role="status"`；六态中文：待配置 / 已配置，未验证 / 正在验证 / 已验证（含模型与时间）/ 配置已变更，需重新验证 / 验证失败。
- 卡片头药丸废除「可用」，与状态条同源同词；首次设置弹层（AnalysisSetupSheet）与设置页（AiModelSettings）共用同一推导函数与同一组件。
- 「已粘贴 N 项凭据」→「已保存 N 项凭据（默认不回显）」；换服务商后旧凭据不显示为当前凭据；清除凭据 → 立即 unconfigured。

### 7.2 主操作与失败行为

- 主按钮统一「保存并验证」（先诊断草稿 → 通过 → 提交 → 写快照；失败不落盘）；次按钮「仅保存」（跳过验证）；对已存配置另有「验证连通」（verify_saved_provider）。
- 诊断失败：表单保留、不落盘、ErrorNote 展示分类结果与动作；不得显示「可用/已连接」。
- 仅保存失败：显示「当前保存状态」实况（SaveOutcome）。
- 测试状态独立于按钮：按钮文案恒定（「保存并验证」「验证连通」），结果进状态条与 ErrorNote，不再塞按钮文字（修复读屏按钮名丢失）。

### 7.3 超时与并发

- 诊断/验证请求后端固定 30s；设置页无长重试。
- 全部异步动作（诊断/拉模型/保存）加 requestId 守卫（仿 KnowledgeHome.tsx:45-71 模式），旧响应返回一律丢弃；切换服务商即作废旧序号。
- 请求中按钮禁用 + `aria-busy`；testing 状态并入 backendLocked（ProviderConnectionForm.tsx:125 现不含 testing，修复）。

### 7.4 错误展示收敛

- SettingsKit 新增 `ErrorNote` 组件：发生了什么 / 最可能原因 / 建议动作 三行 + Collapsible 技术详情（stage、HTTP 状态、脱敏服务商消息、模型 ID）。
- ProviderConnectionForm 表单底部为唯一错误出口；模型拉取错误并入同一 ErrorNote（标注来源「拉取模型」）；删除 `AiModelSettings.tsx:449` 的页面级 props.error 重复渲染；Toast 不再与表单同显同一错误（SettingsPanel.tsx:305-311 修复）。
- 页面级兜底 error 保留但加 `role="alert"`（仅承载非表单类错误）。

## 10. 人工验收边界

代码与 fixture 层验证后，最终报告只写「代码与 fixture 层已验证，真实百炼账号待用户验收」。四家 ASR 真实账号状态逐家列出，不得总括。

**验收注意事项（继承性语义）**：现有取 Key 语义为 env `ECHO_EXTERNAL_AI_API_KEY` 优先于 Keychain（external_ai_gate.rs:57-63）。本方案保持该语义统一（草稿回退路径同源），因此若验收机上存在 env Key，运行时与「已验证」实际验证的都是 env Key——真实账号验收前须确认未设置该环境变量，避免误判。
