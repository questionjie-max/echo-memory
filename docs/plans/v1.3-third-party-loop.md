## 0. 给执行者的硬约束

你是本轮的主实现者。开始前先阅读仓库根目录 `AGENTS.md`、相关代码、测试和本文件。遵守以下规则：

4. 用户已经认可当前视觉风格。**不要重做整体视觉，不要为了“高级感”改版。** 本轮只做信息层级、状态、交互和可访问性修正。
5. 默认本地优先和隐私边界不放松：
   - 未经明确用户动作，不发起第三方请求；
   - Key、Secret、Token 不得进入日志、测试快照、错误正文或最终回复；
   - 自动化测试只能使用 fixture 或假 Key；
   - 未用真实账号验证前，不得写“已验证”。
6. 不碰与当前任务无关的旧问题、旧格式和旧 warning。只修复本轮触发的代码。
7. 所有用户可见文案使用简体中文；必要时同步英文 README，但不要重写整篇文档。
8. 每一项行为变化必须先有失败测试，再实现，再跑全量回归。
9. 若外部真实服务无法在当前环境验证，必须明确标为“待真实账号验收”，不能把 fixture 测试说成真实服务验证。
10. 目标不是“把表单做得更复杂”，而是让用户能明确回答：
    - 我保存的是哪家服务商？
    - 当前 Key 是否存在？
    - 模型目录拉到了什么？
    - 当前模型真的能用于这项能力吗？
    - 如果失败，问题在凭据、网络、模型、权限还是输出格式？
    - 下一步应该点什么？

## 2. 本轮已知问题

### P0-1：百炼可拉模型，但真实分析测试失败

现象：

1. 分析卡选择“阿里云百炼”；
2. 粘贴 Key；
3. 点击“拉取可用模型”成功；
4. 点击测试，真实请求失败；
5. 界面无法说明失败发生在哪一层。

根因方向，不得只选一个未经验证的猜测：

- `/models` 成功只证明 Key、网络和目录权限基本可用，**不证明**当前模型支持 chat、账户有推理权限、模型没有下线，也不证明模型能稳定输出 JSON；
- 百炼推荐模型被硬编码为 `qwen-turbo`，可能已不是最合适或当前可用的文本模型；
- 远端模型列表没有按分析能力筛选，ASR、embedding、rerank、视觉等模型可能被误选；
- 测试读取的是已保存配置，而用户刚刚编辑的是页面草稿，可能测试了上一家服务商或上一个模型；
- “保存并测试”会先写入配置再测试，失败时可能留下半配置；
- 当前实现把所有失败统一压成“失败”，没有显示阶段、HTTP 状态、模型 ID 和下一步。

已知现场线索：

- 本机持久化配置当时仍是旧的 `custom` 分析配置，而不是百炼，说明“页面草稿状态”和“后端已保存状态”可能不一致；
- 因此不能只修 `/models` URL，必须修完整状态机和测试入口。

必须覆盖的失败分类：

| 阶段 | 现象 | 用户结论 | 下一步 |
|---|---|---|---|
| 目录 | `/models` 为 401/403 | Key 无效或无模型目录权限 | 重填 Key / 查看厂商控制台 |
| 目录 | `/models` 网络失败或超时 | 当前无法连接厂商 | 检查网络/代理/地址 |
| 推理 | `/models` 200，chat 401/403 | Key 可读目录，但无推理权限或账户状态异常 | 检查开通、余额、权限、地域 |
| 模型 | chat 404 / model_not_found | 当前模型不存在或账号无权使用 | 从实时列表中选择其他文本模型 |
| 协议 | chat 400 / unsupported_model | 当前模型不支持该接口或参数 | 换文本对话模型 |
| 配额 | 429 | 频率限制或额度不足 | 等待/检查额度 |
| 网络 | 传输错误/超时 | 请求没有完成 | 重试或检查网络 |
| 返回 | 200 但无内容 | 响应格式异常 | 查看脱敏技术详情 |
| 格式 | 200 有内容但不是合法 JSON | 连接可用，模型不满足结构化输出要求 | 换更适合分析的模型 |

分类优先级：

1. 先解析服务商返回的脱敏 `error.code / error.type / error.message`；
2. HTTP 状态只作为辅助信号，不得单独决定“Key 无效”或“模型不存在”；
3. 不同厂商可能用 400、403、404 的任意组合表达 `model_not_found`、模型未开通、无推理权限；
4. 无法可靠分类时，显示“模型或权限不可用”，同时给出“换模型”和“检查账号权限”两个动作；
5. 任何情况下都不能把服务商原始响应、请求头或完整错误体直接展示或写日志。

验收要求：

- 绝不能把“模型目录成功”当成“连接验证成功”；
- 选中不存在、无权限或不支持 chat 的模型时，必须给出具体原因；
- 测试失败后不得显示“可用”或“已连接”；
- 如果 Key 本身可用但模型不可用，提示必须说“换模型”，而不是“检查 Key”。

### P0-2：测试的是已保存配置，不是当前草稿

当前流程：

- 设置页为了测试，先保存 provider/model/consent，再读取后端 Keychain 和数据库执行测试。

问题：

- 用户只是想验证刚粘贴的 Key，却先污染了保存配置；
- 测试失败后不知道新配置是否已经生效；
- 新 Key 写失败时可能留下“新 provider + 旧 Key”的假状态；
- 页面可能仍在展示上一家服务商的状态；
- 同一错误可能被表单、父级卡片、页面底部重复展示。

目标行为：

1. 增加“测试当前草稿”能力；
2. 草稿测试的 Key 只在内存传递，不写 Keychain、不写 SQLite；
3. 测试成功后，用户再明确点击保存；
4. 或提供“保存并验证”：先测草稿，通过后再提交；验证失败时已保存配置保持不变；
5. 任何提交失败都必须明确告诉用户“当前保存状态是什么”，不能留下猜测空间。

验证结果绑定：

- 草稿诊断返回一次性 `verificationToken`，后端在内存中记录它对应的：
  - `providerId`
  - 规范化后的 `baseUrl`
  - `model`
  - 本次输入的凭据集合摘要（只在进程内内存中保存，使用进程随机密钥做 HMAC，不落盘、不返回前端）
  - 过期时间；
- “保存并验证”必须携带该 token；后端重新计算并比对 provider、地址、模型和凭据摘要；
- token 已过期、已使用或任一字段变化时，拒绝复用旧验证结果并要求重新测试；
- token 不跨重启复用；
- 保存成功后写入健康快照，快照只保存非敏感配置与凭据修订号，不保存 Key、Secret 或其裸哈希。

### P0-3：状态语义互相打架

当前出现以下语义混用：

- 配置填齐 = “可用”；
- 保存成功 = “已启用”；
- 测试结果被塞进按钮文字；
- 测试失败后卡片仍可能显示绿色“可用”；
- 首次设置弹层与普通设置页对同一动作使用不同文案和不同行为。

必须建立统一状态机：

```text
未配置
  -> 已配置，尚未验证
  -> 验证中
  -> 已验证
  -> 配置已变更，需要重新验证
  -> 验证失败
```

规则：

- 填齐字段只能进入“已配置，尚未验证”；
- 测试成功或真实任务成功后才能进入“已验证”；
- 修改 provider、Base URL、模型、Key/Secret 后立即回到“配置已变更”；
- 验证失败必须保留“重新验证”和“换用推荐模型/重新填写 Key”等动作；
- 测试状态必须独立于主按钮，不能只存在于按钮文案；
- 状态必须有 `role="status"` 或等价可访问性语义；
- 如果测试是先保存后执行，失败时必须明确显示“配置已保存，验证未通过”。

### P1-1：模型列表没有能力过滤与对账

要求：

- 分析只把明确的文本对话模型作为首选候选；
- 明显属于 `embedding / rerank / asr / tts / speech` 的模型折叠到“其他模型”，不得作为推荐；
- 不确定用途的模型可展示，但必须标记“适用性未知”；
- 转写继续只展示可识别的 ASR 模型；
- 当前模型不在远端列表时显示明确警告；
- **不得静默自动切换到别的模型**；
- 用户必须能明确选择“使用推荐模型”或“保留当前模型继续测试”；
- 拉取模型只刷新候选，不自动保存、不自动改同意、不自动验证。

### P1-2：推荐模型与时效性

要求：

- 不得再用一个可能已经下线的模型作为唯一默认；
- 百炼分析建议从当前通用文本模型中选一个稳定别名，并验证；
- 若推荐模型不在实时列表中，界面显示“推荐模型当前未返回”，提供替代候选；
- Provider Catalog 增加非敏感时效元数据，例如 `catalogUpdatedAt`、`lastVerifiedAt`；
- `lastVerifiedAt` 未真实填写前只能显示“待真实账号验证”，不得伪造；
- 目录版本变化后，旧的“已验证”状态必须失效或标记“目录已更新”。

### P1-3：测试超时和重试不适合设置页

要求：

- 连通测试使用短超时，建议总时长不超过 30 秒；
- 设置页测试不沿用正式分析任务的长时间重试；
- 测试中按钮明确禁用并显示“正在验证当前模型…”；
- 连续点击不能发多个并行请求；
- 切换服务商/模型后，旧请求返回不得覆盖新状态；使用请求序号或取消标记。

### P1-4：错误展示位置和重复

要求：

- 一个错误只在一个就近区域展示；
- 错误结构拆为：
  1. 发生了什么；
  2. 最可能的原因；
  3. 建议动作；
  4. 可折叠技术详情；
- 技术详情显示阶段、HTTP 状态、脱敏服务商消息、模型 ID；
- Key、Secret、Authorization、请求体中的敏感字段必须继续脱敏；
- 设置页底部不得再重复同一错误。

## 3. Phase 0：先完成“第三方连接收口”

Phase 0 不计入后面的四轮产品升级，但它是所有后续工作的前置门。

### 3.1 目标

让一个普通用户能够：

1. 选择百炼；
2. 粘贴 Key；
3. 拉取实时模型；
4. 看懂哪些模型适合分析；
5. 用当前草稿做一次真实小请求；
6. 如果失败，知道该换 Key、换模型、检查权限还是检查网络；
7. 验证通过后再保存；
8. 保存后卡片状态与验证结果一致；
9. 重启应用后仍能看到验证结果；
10. 改任何相关内容后，旧验证立即失效。

### 3.2 接口要求

可以按现有代码风格命名，但语义必须完整。

#### 草稿诊断

新增一个不落盘的诊断入口，输入至少包括：

```text
target: analysis | transcription
providerId
baseUrl
model
credentials?: 表单新凭据；为空时可用当前槽位的已保存凭据
```

输出结构化结果：

```text
stage
status
model
httpStatus?
errorCode?
sanitizedProviderMessage?
testedAt
suggestedAction
```

要求：

- 分析测试只发送固定的小提示词，不包含用户录音、逐字稿、知识库内容；
- 转写测试只发送约 1 秒固定测试音频；
- 测试请求不写数据库、不写 Keychain；
- 不把测试用的新 Key 返回前端；
- 所有错误继续经过现有脱敏链路；
- 未保存 Key 时，不能偷偷读取另一家服务商的 Key。

草稿诊断是新增网络入口，必须完整复用现有安全边界，不能只校验字段非空：

- 内置服务商只允许 Provider Catalog 中的固定地址；
- 自定义地址必须走 `validate_external_base_url`，只允许 HTTPS，本机 loopback 例外；
- 发请求前必须走 `assert_endpoint_still_safe`，防止 DNS rebinding；
- 禁止重定向，保持 `redirects(0)`；
- 限制 URL 长度、响应体大小和总超时；
- 固定请求方法和固定测试请求体，不接受调用方注入任意路径、任意 Header 或任意请求体；
- 新 Key 只在命令调用栈和短期内存校验状态中存在，不进入日志、事件、错误详情、测试快照或前端持久状态；
- 错误信息继续对 Key、Secret、Authorization 和敏感请求字段脱敏。

#### 提交

“保存”和“测试”解耦：

```text
保存配置
保存并验证
验证当前已保存配置
```

“保存并验证”必须先验证草稿，再提交。验证失败时，原保存配置不得变化。

如果提交阶段仍可能发生 DB 或 Keychain 失败，必须：

- 先用一个后端命令统一编排；
- 尽力回滚凭据与设置；
- 回滚失败时返回明确的部分状态；
- UI 重新读取后端真实状态，不能相信本地乐观状态。

### 3.3 模型候选规则

分析：

1. 推荐模型；
2. 当前已选模型；
3. 远端返回的明确文本/对话模型；
4. 其他模型放进折叠组；
5. 手动模型 ID 继续保留。

转写：

1. 内置推荐；
2. 当前已选；
3. 远端可识别 ASR 模型；
4. 手动模型 ID。

规则：

- 远端候选必须携带来源：`recommended / remote / manual / current`；
- 当前模型不在实时列表时显示警告，但不自动替换；该警告只对声明了 `supportsModelList` 的服务商生效；
- `/models` 返回空列表时显示“服务商没有返回可用模型”，不显示“拉取成功”；
- 远端重复模型先去重、稳定排序，再参与当前模型对账；
- 用户改变模型后，同意和验证状态立即失效；
- 用户切回原配置时，旧验证也不能自动恢复，除非有完整配置指纹且未发生变化。

### 3.4 状态展示

卡片头部、表单状态条和操作按钮共享同一状态：

| 状态 | 卡片 | 主操作 | 说明 |
|---|---|---|---|
| 未配置 | 待配置 | 填写凭据 | 不显示可用 |
| 已配置未验证 | 已配置，未验证 | 保存并验证 | 可用性未知 |
| 验证中 | 正在验证 | 禁用 | 不重复发请求 |
| 已验证 | 已验证 | 重新验证 | 显示模型与时间 |
| 配置已变更 | 需重新验证 | 保存并验证 | 旧结果已失效 |
| 验证失败 | 验证失败 | 重试/换模型 | 展示可行动原因 |

不要用“已连接”描述只拉取过模型列表的状态。

验证持久化规则：

- 每次保存分析或转写凭据时，递增该槽位的 `credentialRevision`；
- 健康快照包含：provider、baseUrl、model、credentialRevision、catalogVersion、testedAt、stage、status、非敏感 errorCode；
- 重启后，只有 provider、baseUrl、model、credentialRevision、catalogVersion 全部匹配时才显示“已验证”；
- 任一字段变化都必须显示“配置已变更，需要重新验证”；
- 不得保存 Key 本身、Key 的裸哈希或可离线反推 Key 的材料；
- 如果实现无法保证以上条件，降级文案只能是“上次测试通过”，不能显示“已验证”。

### 3.5 凭据文案

- “已粘贴 N 项凭据”改为“已保存 N 项凭据”；
- 明确“默认不回显”；
- “修改”必须重填完整凭据；
- 更换服务商后，旧服务商凭据不能继续显示为当前凭据；
- 清除凭据后，状态立即回到“未配置”；
- 跨卡复用时保持现有安全边界，不经过前端秘密值。

### 3.6 Phase 0 必须增加的测试

Rust：

- 百炼 `/models` 200，chat 404，结果归类为“模型不可用”；
- `/models` 200，chat 401/403，结果归类为“Key 无推理权限”；
- chat 429、timeout、非 JSON、无 content 各有独立分类；
- 草稿测试不写数据库、不写 Keychain；
- 草稿测试不会读取另一服务商的已保存 Key；
- 草稿诊断与保存之间使用一次性 token；字段变化、token 过期或重复使用都必须拒绝复用验证结果；
- 自定义地址草稿测试覆盖 SSRF、DNS 复校、重定向和协议边界；
- 凭据修订号变化后，旧验证状态立即失效；
- 验证失败后原保存配置完全不变；
- 配置提交失败时不留下“新 provider + 旧 Key”的静默可用状态；
- 错误正文不包含测试 Key；
- 模型分类不会把 embedding/rerank/asr 放进分析推荐；
- 当前模型不在远端列表时有明确状态。
- 不支持 `/models` 的服务商不会出现“当前模型不在列表”的错误警告；
- 空模型列表、重复模型和推荐模型缺失都有独立测试。

前端：

- 测试失败后卡片不能显示“可用”；
- 修改 provider/model/credentials 后验证状态立即失效；
- 拉取模型成功不自动保存；
- “保存并验证”失败时保留表单并说明当前保存状态；
- 重新拉取模型时只有一个主模型选择器；
- 错误只出现一次；
- 状态条有可访问性语义；
- 首次设置弹层和普通设置页行为一致；
- 860×600 最小窗口下按钮、状态与错误不溢出。

验证命令：

```bash
cd app
npm run typecheck
npm run test:ui
npm run build

cd src-tauri
cargo test

cd ..
git diff --check
```

如仓库另有与本轮相关的 growth 测试，一并运行。不要为了通过格式检查批量格式化全仓库。

### 3.7 Phase 0 人工验收

由用户使用自己的真实百炼账号完成：

1. 选择“阿里云百炼”；
2. 粘贴新 Key；
3. 拉取模型；
4. 确认列表能区分文本模型与其他模型；
5. 选择可用文本模型；
6. 测试草稿；
7. 成功后保存；
8. 重启应用，验证状态仍在；
9. 修改模型，确认状态变为“需重新验证”；
10. 选择不兼容模型，确认提示是“模型不适用于分析”，而不是“Key 无效”。

在用户完成这 10 步前，最终报告只能写：

> 代码与 fixture 层已验证，真实百炼账号待用户验收。

## 4. Loop 运行方式

Phase 0 通过后，进入四轮产品自进化。

### 4.1 每轮固定角色

最多同时使用三个分析子代理，不参与直接写文件：

1. **产品功能代理**
   - 找真实用户问题；
   - 明确数据与状态不变量；
   - 给出后端/接口/测试方案；
   - 防止只做视觉层。
2. **用户体验代理**
   - 走首次使用、日常使用、失败恢复三条旅程；
   - 找出多余步骤、死路、误导状态；
   - 写出可验证的用户场景。
3. **UI/交互代理**
   - 评估信息层级、控件的出现时机、空/错/加载状态、键盘与可访问性；
   - 不重做已认可的整体风格；
   - 只提出能减少认知负担的改动。

另设一次独立代码评审。评审者不能是主要实现者；如果环境只有主代理，则必须用独立的新上下文做一次“审稿式”代码审查，不能边写边自评代替。

### 4.2 每轮开始时的候选筛选

每个子代理提出 2–3 个新方向，并逐项标注：

- 解决什么用户问题；
- 当前证据；
- 对产品价值的增量；
- 与已完成方向的差异；
- 最小可交付范围；
- 风险与回滚点；
- 需要哪些测试与人工验收。

主代理汇总后必须先检查“不要重复清单”。任何与旧方向重复的提案直接淘汰。

每轮只选：

- 1 个主方向；
- 最多 2 个直接服务于主方向的支撑修复。

如果一个方向需要跨 5 个以上页面重做，拆成后续轮次。

### 4.3 每轮固定门禁

```text
G0 方向门
  -> 三个代理独立提案
  -> 主代理去重、评分、定一个主方向

G1 方案门
  -> 写清用户场景、状态机、数据/接口、非目标、测试矩阵
  -> 独立评审指出漏洞
  -> 修方案后再实现

G2 实现门
  -> 先写失败测试
  -> 最小实现
  -> 前端/后端/文档同步

G3 验证门
  -> 本轮定向测试
  -> 全量 test/build
  -> 最小窗口与可访问性检查
  -> git diff --check

G4 代码评审门
  -> 独立 review
  -> P0/P1 必须修
  -> review 通过后重跑全量

G5 复盘门
  -> 写 round report
  -> 更新排除清单
  -> 给下一轮至少 3 个素材方向
```

任一 P0/P1 未关闭，不得进入下一轮。

### 4.4 每轮独立代码评审清单

评审者必须检查：

- 行为是否真的解决用户问题，而不是只改文案或按钮；
- 是否出现第二套真实状态来源；
- 是否存在“已保存 / 已配置 / 已验证 / 可用”混用；
- 是否在错误路径留下半配置；
- 是否把秘密写入日志、测试、错误或文档；
- 是否在未同意时发送用户内容；
- 是否只靠 mock 测试而没有命令/状态集成测试；
- 是否有重复错误、重复请求、竞态和旧响应覆盖新状态；
- 是否有无边界的轮询、长阻塞或不可取消任务；
- 是否破坏旧数据、旧设置和本地优先；
- 是否改动无关文件、顺手重构或格式化；
- 是否有真实空态、错误态、键盘/读屏路径。

评审输出格式：

```text
[P0] 阻断发布，必须修
[P1] 应在合并前修
[P2] 可记录，不阻断
[question] 需要信息才能判断
[praise] 值得保留的设计
```

## 5. 四轮产品升级

以下四轮是预设方向，但每轮仍必须经过代理讨论和证据复核后才能动手。

### Round 1：AI 任务中心与可恢复运行

用户问题：

- 转写、分析、索引、模型下载的状态散落在不同页面；
- 第三方任务耗时长、可能计费，失败后用户不知道从哪继续；
- 当前状态可能只在某个卡片里看得到。

目标：

- 把后台任务统一成一份可见、可恢复的运行视图；
- 后端 job 状态是唯一真相；
- 工具栏显示“运行中 N 项”，点开进入任务抽屉；
- 任务详情显示：类型、记录/对象、服务商、模型、当前阶段、进度（有就显示）、开始时间、失败原因、是否可取消、是否会产生第三方请求；
- 支持重试和取消，但不能生成重复任务；
- 应用重启后能恢复显示；
- 记录详情只提供该任务入口，不复制第二套状态逻辑。

非目标：

- 不重写队列系统；
- 不增加后台常驻代理；
- 不伪造 ETA；
- 不把模型下载 UI 重做一次。

验收：

- 转写、分析同时运行时，任务中心完整显示；
- 取消后后端状态与 UI 一致；
- 进程重启后，历史中断任务按现有恢复机制显示；
- 任务中心与记录详情状态不矛盾；
- 无轮询风暴，失败事件可感知但不重复打扰；
- 相关单元/集成/UI 测试覆盖。

### Round 2：首次获得真实结果的更短路径

用户问题：

- 首次使用仍要先理解模型、服务商、Key、同意和索引；
- 用户在完成这些配置前看不到这个产品最终能交付什么；
- “配置成功”不是用户价值，“第一份可用的会议结论”才是。

目标：

- 提供一条不污染真实资料库的“示例体验”路径；
- 用一个明确的示例会议/访谈，展示逐字稿、带证据摘要、待办、行动闭环和导出；
- 示例必须明示是演示数据，不能伪装成用户录音；
- 示例不进入 MCP，不进入用户自己的记忆；
- 用户完成示例后，再引导用自己的第一条录音完成真实激活；
- 如果当前模型/服务商未就绪，可以明确标注哪些步骤是预生成示例，不能伪造实时进度。

动工前先做技术预研：

- 示例数据放在哪个隔离目录；
- 如何确保不出现在真实搜索、MCP、记忆确认和导出历史；
- 如果隔离边界需要改动过多现有查询，则缩小为只读静态演示，不承诺完整交互。

非目标：

- 不重复修 Onboarding 自动弹窗等 v1.2 已处理问题；
- 不强制走完全部步骤；
- 不把示例结果写进真实知识库；
- 不为示例引入云端用户数据。

验收：

- 新用户能在不配置模型的情况下看到完整样例链路；
- 所有示例数据有清晰标识和退出入口；
- 示例不会出现在真实搜索、MCP、记忆确认、导出历史中；
- 删除示例不触碰真实数据；
- 首次真实任务完成时，状态有明确“从现在开始是你的真实资料”的边界。

### Round 3：跨会议连续性与行动闭环

用户问题：

- 单次会议有摘要，但项目下一次会议不知道“上次决定了什么、哪些行动还没完成”；
- 用户需要在多个记录、行动项和成长视图之间手工拼接上下文；
- 记忆系统的价值应体现为连续工作，而不是一堆独立总结。

目标：

- 在项目维度展示会议系列的前后关系；
- 突出上次决策、假设变化、未完成行动与本次结果；
- 每条关联必须能回到原始逐字稿或证据片段；
- 行动只能由用户确认完成，不能因为新会议提到“已完成”就自动标记；
- 不把推断关系伪装成用户确认事实；
- 优先复用现有 project、analysis、minutes_items、action_items 数据，不新增无必要的宽表。

非目标：

- 不重复现有的成长轨迹/认知演化视图；
- 不构建团队协作或任务管理平台；
- 不自动发送提醒、邮件或日程；
- 不让模型自由生成“上次承诺”而无需证据。

验收：

- 每个“上次/本次”关联都有证据；
- 找不到证据时显示“未找到可靠关联”，而不是编造；
- 归档记录不进入当前连续性视图；
- 未确认行动不会被标记为已完成；
- 项目无历史、只有一条记录、跨知识库等边界都有测试；
- 对性能有基本测量，避免 500 条记录时不可用。

### Round 4：专家效率与视觉降噪

用户问题：

- 高频用户需要键盘操作、筛选、批量动作和更少视觉噪音；
- 当前状态和操作逐渐增多，信息层级需要收束；
- 不能以“高级功能”为名增加隐藏操作。

目标：

- 增加命令面板和常用键盘导航；
- 支持保存常用筛选视图；
- 统一状态颜色、空态、错误态、焦点态；
- 设置页只展示当前任务需要的内容，高级参数渐进展开；
- 优化窄窗口、键盘焦点顺序、ARIA 与 reduced motion；
- 至少完成一次可用性走查，记录真实截图与问题。

非目标：

- 不重做整体视觉；
- 不用纯图标替代清晰文字；
- 不牺牲空态和错误态的明确性；
- 不添加未经用户请求的复杂自定义能力。

验收：

- 主流程可完全键盘完成；
- 焦点可见，弹层焦点不逃逸；
- 860×600 窗口下无关键操作溢出；
- 空/错/加载状态有统一结构；
- 命令面板不会执行破坏性操作而不确认；
- 所有新增交互至少有 UI 测试或人工证据。

## 6. 明确不要重复的方向

以下内容已经完成、已经讨论过，或明确排除。四轮中不得重新作为主方向：

- Provider Catalog 基础架构；

## 8. 最终完成定义

全部四轮结束后，必须满足：

1. Phase 0 的所有 P0/P1 关闭；
2. 四轮各有独立报告和交接材料；

## 9. 现在立刻执行的顺序

1. 读取 `AGENTS.md`、`git status`、`git diff --stat`；
2. 运行当前基线测试，记录真实数量；
3. 启动三个只读分析代理，分别讨论：
   - Provider 连接的真实性、状态机与模型能力；
   - 用户首次配置、失败恢复与日常流程；
   - 设置页信息层级、状态表达、可访问性与最小窗口；
4. 汇总并写出 Phase 0 详细方案；
5. 由独立评审先审方案，P0/P1 方案问题修完再写代码；
6. 以失败测试驱动完成 Phase 0；
7. 跑全量验证并做独立代码评审；
8. 请用户用真实百炼账号执行第 3.7 节的 10 步验收；
9. 用户确认后，进入 Round 1；
10. 以此类推，每轮开始先讨论、查重、评审，再实现；每轮结束写报告、做代码评审、更新素材，再进入下一轮。

不要跳过第 8 步的“待用户验收”标记，也不要在 Phase 0 未闭环时开始四轮功能升级。
