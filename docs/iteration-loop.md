# 回声记忆 · 产品完善循环与结构路线（Loop 设计方案）

> 本文档定义回声记忆从 Alpha 走向 1.0 的迭代循环与产品结构补全计划。
> 它是 2026-08 v0.2.0 → v0.4.4 四轮实战（三次热修均由真实用户实测发现）的经验沉淀，
> 也是后续所有版本的执行依据。每个里程碑结束时回顾并修订本文。

---

## 一、为什么需要显式的 Loop

v0.4.x 连续三个热修的教训：主线程冻结（0.4.1）、设置面板永不加载（0.4.2）、弹窗透明（0.4.3）——
**全部只有真人点一遍才能发现**。后端 106 项测试全绿的同时，GUI 层可以是坏的。
结论：光有代码测试不够，必须有一个把「构建 → 对抗测试 → 真实使用 → 热修」固定下来的循环，
并且每一层循环有自己的质量门禁。

两个反复出现的陷阱，写在这里备查：

- **`.material` 这个类名在 CSS 里从来没有定义过**（全仓只有引用、没有规则）。
  面板的背景、边框、阴影必须由自己的类提供，否则就是一块透明板压在遮罩上 —— v0.4.3 和
  v0.5.1 的引导面板都栽在这里。G1 清单第 1 条就是盯它的。
- **同一个东西在两个地方各有一套事实**，界面就会自相矛盾。已安装模型的 id 是文件名去后缀
  （`ggml-large-v3-turbo-q5_0`），推荐模型的 id 是 `large-v3-turbo-q5_0`，拿 id 比对的结果就是
  「装好了还让你下载」。凡是跨端传递的标识，只保留一处来源，并且用可比对的形式（文件名）传。

## 二、三层循环

```
┌─────────────────────────────────────────────────────────────┐
│ 大循环（里程碑级，1 个版本主题，3-7 天）                        │
│  结构评审 → 主题开发 → 出口门禁 → 发 DMG → 用户实测窗口         │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ 中循环（版本内，每个功能，0.5-1 天）                      │  │
│  │   设计确认 → 实现 → 对抗自查 → 合入分支                   │  │
│  │   ┌─────────────────────────────────────────────────┐ │  │
│  │   │ 微循环（每次提交，分钟级）                          │ │  │
│  │   │   写码 → G0 门禁 → 提交                           │ │  │
│  │   └─────────────────────────────────────────────────┘ │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 微循环 · G0 门禁（每次提交必须全绿）

```bash
cd app
npm run typecheck && npm run build && npm run test:growth && npm run test:ui
cd src-tauri
cargo fmt --check && cargo test --features mcp-bin
```

任何一项不过，不提交。这是底线，没有例外。

### 中循环 · 功能级（每个功能完成时）

1. **实现前**：一句话写清行为定义（谁、在哪个入口、期望结果、失败时的表现）
2. **实现后对抗自查**（站在"想让它坏"的视角，至少过一遍）：
   - 空状态 / 首次使用（无数据、无模型、无配置）会怎样？
   - 慢路径：本地模型 10-30 秒的调用，是否全部在后台线程？（0.4.1 教训）
   - 前端加载失败时用户看到什么？是否永远停在"正在读取…"？（0.4.2 教训）
   - 新增 UI 是否有自己的背景/边框/阴影，不依赖不存在的类？（0.4.3 教训）
   - 中文/IME 输入、重名、超长文本、并发双击
3. **真实环境验证**：能用真实模型跑的，用 `ECHO_E2E=1` 跑 `realworld_e2e_test`（TTS 生成真实语音 → 全链路）
4. 合入开发分支，不打 DMG

### 大循环 · 版本级（发 DMG 前后）

**发布前 · G1 门禁（GUI 冒烟清单，人工 10 分钟）**：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 冷启动 | 全新资料库能启动，引导向导出现，且向导卡片本身有背景和阴影（不能是透明板压在遮罩上） |
| 2 | 设置六个 tab 逐一打开 | 每个都出数据，无"正在读取…"停留超 2 秒 |
| 2b | AI 模型 tab：点模型行即生效 | 点一行就切过去并弹出「已保存」，页面里不存在「保存设置」按钮 |
| 2c | AI 模型 tab：下载与续传 | 下载中行内出百分比和字节数、可取消；中断后按钮变「继续下载」并显示已下多少；下完自动成为当前模型 |
| 3 | Dock 对话（本地） | 发送期间界面可点、可切视图，回复正常渲染；入口名是「随行助手」，默认模式「随手问」并说明不读资料库 |
| 3b | 顶栏版式稳定 | 五个视图来回切换，主导航位置不动、顶栏搜索框常驻；任一视图搜索都能把记录打开到首页 |
| 3c | 问知识库单一入口 | 知识库主页只有「问知识库 →」跳转按钮，不再有第二套问答界面 |
| 4 | 模板向导 | 弹窗有背景，完整走一轮 满意/不满意 |
| 5 | 拖入/导入一段音频 | 状态流转到分析完成，详情页可播可跳转 |
| 6 | 关于 tab | 版本号正确，复制数据目录可用 |
| 7 | 升级路径 | 用旧版本真实资料库启动，数据完好 |
| 8 | 干净机器（发 DMG 前必做一次） | 在没有其它语音软件、没有 whisper 环境变量的机器上：下载推荐模型 → 直接能转写，不报「未找到模型」 |

**发布后 · 用户实测窗口（1-2 天）**：
- 你以真实用户身份使用，问题直接报现象（截图/崩溃报告最好）
- 热修 SLA：阻塞性问题（崩溃/冻结/核心功能不可用）当天修复发 x.x.x+1；
  体验类问题归入下一版本
- 连续一个实测窗口无热修 → 该版本视为稳定，触发里程碑动作（合并 main、打 tag）

**里程碑 · 结构评审（每个版本主题开始前）**：
对照下方五层结构矩阵检查——本主题补哪层？是否引入了新的结构债？
并强制配额：**每个版本至少偿还一项技术债**（见第四节）。

## 三、产品结构现状矩阵（对照「采集→感知→记忆→理解→行动」五层架构）

| 层 | 已具备 | 缺口 | 补全版本 |
|---|---|---|---|
| **采集** | 音频收件箱（文件夹监听+USB 扫描+基线防误导）、文档导入、拖拽 | 菜单栏快速录音、全局热键、手机端 | v0.7.0 |
| **感知** | Whisper 本地转写（分块/预热 prompt）、热词注入、AI 校对、繁简归一 | **说话人分离**（全部标"未知"）、词级时间戳 | **v0.5.0** |
| **记忆** | SQLite+FTS+向量混合检索、版本化逐字稿、认知演化快照、相关记录 | 实体关系图谱（人/项目/主题）、跨记录推理、"我的记忆"总览 | v1.0 Beta |
| **理解** | Ollama 结构化分析（证据引用+防幻觉校验）、Dock 四模式对话、模板向导 | 更大默认模型建议、外部引擎对话记忆、长录音分段摘要策略 | 随版本演进 |
| **行动** | MCP 只读 6 工具、行动仪表盘、产出文件夹（开放出口） | MCP 观点演化/图谱查询、待办外发（提醒/日历）、MCP 受控写入 | v0.8.0 |

## 四、版本路线（每版本 = 一个主题 + 一项技术债）

| 版本 | 主题 | 内容 | 技术债配额 |
|---|---|---|---|
| **v0.5.0** | 谁在说话 | whisperX 外置引擎（可选）、说话人重命名、行动项归属说话人、人名进热词建议 | **GUI 冒烟自动化起步**（tauri-driver 或最小 e2e）；设置面板/向导组件测试 |
| **v0.6.0** | 可分发（主题已调整，2026-09-21） | 转写长录音幻觉修复（P0）+ 退化检测不覆盖、分析可达性（Ollama 墙）、未签名分发指引、模型下载国内可用、干净机器全流程、DMG + GitHub Releases | repository.rs 拆分（按领域拆模块，行为不变） |
| **v0.7.0** | 捕捉无感化 | 菜单栏常驻 + 全局热键快速录音、录音即时转写（流式探索） | 轮询架构 → Tauri 事件推送（RecordDetail 2 秒轮询退役） |
| **v0.8.0** | 记忆可行动 | MCP 新工具（演化查询/图谱/行动项）、产出自动化（定期周报 md） | CSP 收紧 + commands.rs 拆分 |
| **v0.9.0** | 打磨 | 大库性能（万段级）、onboarding 完善、错误信息人性化 | 前端组件测试覆盖核心三视图 |
| **v1.0 Beta** | 记忆有结构（原 v0.6.0 主题后移） | 实体抽取（人/项目/主题）、关系图谱视图、"问我的记忆"跨记录问答 + Apple 开发者账号 + 签名公证、自动更新 | — |

**节奏约定**：主题开发 3-5 天 → DMG → 实测窗口 1-2 天 → 热修 → 合并 main。
不赶进度：一个版本没过 G1 + 实测窗口，不进下一主题。

## 五、Loop 的度量（每个里程碑回顾时看四个数）

1. **热修数**：目标 ≤1/版本；连续两版本 0 热修 → GUI 冒烟清单可考虑升级为自动化
2. **实测反馈响应时长**：从你报告到修复 DMG，目标 <1 天
3. **E2E 覆盖**：realworld_e2e 断言的功能数（当前 8 步，只增不减）
4. **结构债余额**：第四节矩阵中"缺口"项数量趋势

## 六、角色分工

- **构建者（AI）**：设计、实现、对抗自查、真实环境 E2E、热修
- **真实用户（你）**：版本实测窗口的原型用户——只报现象和感受，不定位原因；
  连续使用无阻塞性问题即放行
- **决策点**：每个版本主题开始前确认范围；实测窗口结束决定合并或继续修
